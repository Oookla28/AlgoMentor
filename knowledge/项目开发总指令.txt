# 项目开发总指令
# 数构智学——基于多工具智能体、可信知识检索与知识追踪的数据结构与算法智能助教平台

## 0. 你的身份与任务

你是一名资深 Python 全栈架构师、Django 工程师、LLM Agent 工程师、RAG 工程师、教育智能系统研究员、算法工程师与软件测试工程师。

你需要独立完成一个完整、可运行、可维护、可测试、可交付的数据结构与算法智能助教平台。

项目正式名称：

数构智学

英文工程名称：

AlgoMentor

项目副标题：

基于多工具智能体与知识追踪的自适应算法学习平台

本项目不是概念展示、静态网页、UI 原型或单纯的大模型聊天工具。

最终必须交付实际可以运行的 Django Web 系统。

系统必须能够完成：

1. 用户注册、登录与个人配置。
2. 用户自行填写 DeepSeek API Key。
3. 用户在三个 DeepSeek 模型档位之间切换。
4. 课程知识库 RAG 问答。
5. LangChain Agent 自主选择真实工具。
6. Python 代码真实执行与自动评测。
7. 学生真实做题记录管理。
8. 智能错题诊断。
9. 自适应算法教学。
10. 个性化题目推荐。
11. 数据结构与算法可视化。
12. 基于真实学习行为的知识掌握程度计算。
13. 可以动态点亮的知识网络图。
14. 知识依赖分析与学习路径规划。
15. CrewAI 多智能体学习报告。
16. RAG、Agent、代码评测的系统实验与验证。
17. 完整的异常处理、日志、安全防护和部署文档。

所有模块必须形成完整的数据闭环。

不允许将任何要求仅实现为静态页面、虚构数据或不可执行的伪代码。

不得在尚未开发和测试时声称某项功能已经完成。

如果某个外部服务需要 API Key、授权或用户配置，必须实现真实的配置流程及错误提示。

不得伪造服务连接成功、代码评测结果、Agent 调用记录或学习实验数据。

# 第二部分：工程质量与总体开发原则

## 4. 项目必须达到的工程标准

本项目必须以长期维护为前提。

遵循以下设计原则：

### 4.1 高内聚、低耦合

每个模块只负责自己的业务领域。

不同模块通过明确的服务接口协作。

不要在一个文件中混写：

- HTTP 请求处理
- 数据库查询
- 大模型调用
- RAG 检索
- 代码评测
- 掌握度计算
- 报告生成

### 4.2 不过度设计

不需要微服务架构。

不需要 Kubernetes。

不需要消息队列集群。

不需要复杂的分布式数据库。

当前项目优先使用：

Django Modular Monolith

即模块化单体架构。

所有业务在一个 Django 项目中完成，但内部具有明确边界。

### 4.3 服务分层

采用以下层次：

Presentation Layer
    ↓
Application Service Layer
    ↓
Domain Logic Layer
    ↓
Infrastructure Layer

其中：

Presentation：
Django Views、Forms、Templates。

Application：
任务编排、事务协调、应用服务。

Domain：
掌握度算法、知识依赖规则、推荐规则、评测规则。

Infrastructure：
DeepSeek API、Chroma、代码执行 API、外部搜索服务、日志存储。

### 4.4 依赖方向

业务层不能反向依赖页面层。

掌握度算法不能直接操作 HTTP Request。

知识网络布局不能直接依赖 Django View。

AI 服务不能直接修改掌握度数据。

外部 API 客户端不得直接决定学生成绩。

### 4.5 可替换性

必须为以下功能定义适配接口：

LLMProvider
EmbeddingProvider
VectorStore
CodeExecutionProvider
ExternalKnowledgeProvider
MasteryEstimator
GraphLayoutProvider

但不要为了抽象而抽象。

每个抽象必须对应实际存在的替换需求。

### 4.6 强类型与数据契约

重要业务服务使用：

- Python 类型注解
- dataclass
- 必要时 Pydantic
- 明确的返回类型
- 统一异常类型

禁止大量依赖不受约束的 dict 在模块之间传递。

### 4.7 数据库访问规范

使用 Django ORM。

禁止直接拼接 SQL。

复杂统计可以使用 ORM 聚合。

所有涉及学生身份的数据查询必须限定当前认证用户。

### 4.8 统一错误处理

建立统一异常结构：

BusinessError
ValidationError
LLMProviderError
AuthenticationError
CodeExecutionError
KnowledgeRetrievalError
ReportGenerationError
ExternalServiceError

根据错误类型返回合理 HTTP 状态码。

前端展示用户能理解的错误信息。

日志记录完整的技术错误，但不能记录 API Key。

# 第四部分：DeepSeek API 与个人密钥管理

## 6. 用户自行填写 API Key

本项目采用 BYOK：

Bring Your Own Key。

所有学生自行提供 DeepSeek API Key。

平台不得要求管理员统一提供一个共享 Key。

用户登录后，进入：

设置 → AI 模型配置

页面包含：

- DeepSeek API Key 输入框
- 当前密钥配置状态
- 默认模型档位
- 测试连接
- 保存配置
- 删除密钥
- 重新配置
- 最近请求状态
- 本月 Token 消耗统计（以实际返回的 usage 为准）

Base URL 默认固定为：

https://api.deepseek.com

普通学生不能输入任意外部 Base URL。

如需支持代理地址，只允许管理员通过服务端环境变量配置经过审核的地址。

防止用户借此构造 SSRF 攻击。


## 7. 三个模型选择档位

界面必须提供以下三个选项。

### 模型一：DeepSeek 极速

DeepSeek 极速

deepseek-flash

非思考模式

- 日常知识问答
- 简单概念解释
- 基础学习提示
- 低复杂度对话

### 模型二：DeepSeek 深度

显示：

DeepSeek 深度

实际 model：

deepseek-flash

模式：

思考模式

high

适用：

- 算法原理分析
- 代码错误诊断
- 复杂知识问答
- 多工具任务

### 模型三：DeepSeek 专家

显示：

DeepSeek 专家

实际 model：

deepseek-v4-pro

模式：

思考模式

默认 reasoning_effort：

high

用户可以在高级设置中切换支持的推理强度。

适用：

- 困难算法分析
- 多步骤推理
- 复杂 Agent 任务
- 学习方案规划

模型参数必须符合官方接口规范。

思考模式参数、输出限制、工具调用和 reasoning_content 的处理必须经过实际兼容性验证。

特别注意：

思考模式和工具调用同时使用时，需要正确处理模型返回的 reasoning_content。

不得因为丢失相关消息字段导致后续 Agent 请求失败。

如果所用 LangChain 版本与 DeepSeek 思考模式存在兼容性问题，应通过独立适配层解决，并增加集成测试。

不得悄悄把已经选择的模型替换成其他模型。

发生降级时必须明确提示用户。


## 8. API Key 安全要求

禁止明文存储 API Key。

使用：

cryptography.fernet

提供：

- 加密保存
- 按当前用户解密
- 更新密钥
- 删除密钥
- 密钥轮换支持

服务端加密主密钥通过环境变量提供。

例如：

APP_ENCRYPTION_KEY

不得把主密钥提交到 Git。

不能把用户 API Key 保存到：

- 浏览器 LocalStorage
- SessionStorage
- HTML 隐藏字段
- 前端 JavaScript 全局变量
- 日志
- 异常信息
- Agent Trace
- Git 仓库

用户重新打开设置页时：

只显示：

已配置

以及安全的掩码标识。

不回传完整密钥。

用户可以自行删除自己的密钥。

所有大模型调用只能由 Django 后端发起。

每次调用都通过当前登录用户找到其对应配置。

不同用户绝对不能共用或读取彼此的密钥。

### API 连接验证

实现：

POST /api/settings/deepseek/test/

流程：

1. 验证当前用户身份。
2. 检查用户是否已经提供密钥。
3. 调用 DeepSeek 官方接口。
4. 验证认证状态。
5. 必要时进行一次最小模型请求。
6. 返回连接状态与模型可用性。
7. 不返回 Key。
8. 不在日志中写入 Key。

单纯获取模型列表成功，不得直接等同于模型推理调用和余额一定可用。

需要分别处理：

- 401 密钥错误
- 402 或余额不足等服务商错误
- 429 限流
- 网络超时
- 服务不可用
- 模型不存在
- 上游错误

### API 消耗控制

每个用户独立记录：

- 模型
- 请求时间
- 请求耗时
- 输入 Token
- 输出 Token
- 请求状态

提供可配置的每日请求次数和 Token 使用上限。

实际费用只能根据服务商公开价格和真实 usage 估算。

不得将估算费用显示成已经扣费的精确账单。


# 第五部分：可信 RAG 知识库系统

## 9. 文档入库

原始文档必须存放在：

knowledge/original/

实现 Django 管理命令：

python manage.py ingest_knowledge

执行：

1. 检查文件。
2. 读取 PDF。
3. 提取原文。
4. 清理无关排版字符。
5. 识别章节。
6. 识别小节。
7. 根据标题和语义边界切分。
8. 保存来源元数据。
9. 生成 Embedding。
10. 写入 Chroma。
11. 验证索引结果。
12. 输出入库统计。

必须支持重复执行。

重复入库同一文件不得产生大量重复记录。

根据文件哈希和文档版本建立索引标识。

不得每次 Django 启动都重新计算整个知识库的 Embedding。


## 10. 知识库范围

根据老师的原始文档建立课程知识体系。

第三章：

第四章：
串、数组和广义表。

不能只建立四个章节节点。

知识库原文和补充知识必须明确区分。


## 11. Embedding

优先采用适合中文文本的本地 Embedding 模型。

例如经过验证的 BGE 中文或多语言模型。

Embedding 必须与生成模型分离。

DeepSeek 负责大模型生成与 Agent。

本地 Embedding 负责知识向量化。

允许通过配置更换 Embedding 模型。

必须记录：

- 模型名称
- 模型版本
- 向量维度
- 索引版本
- 文档版本

不同维度的向量不得直接混合。

更换 Embedding 模型后必须重新建立对应索引。


## 12. 检索优化

基础流程：

→ Embedding

→ Top-K 文档
→ LLM
→ Answer

增强流程：

→ 结果融合

→ 上下文压缩
→ 答案生成

可以采用：

+
BM25
+
Reciprocal Rank Fusion

但必须通过实验确认增加复杂度确实带来收益。

不允许仅为了在报告里写“混合检索”，就添加一个没有实际作用的算法。

禁止编造页码。

禁止让模型自由生成未经校验的文献引用。


## 14. 知识库勘误机制

原始知识库中存在需要核验的示例和公式问题。

必须保留原文。

不得直接覆盖老师提供的 PDF。

独立建立：

KnowledgeCorrection

至少记录：

- 关联原文
- 原始表述
- 建议修改
- 修改理由
- 验证方式
- 审核状态
- 审核人员
- 创建时间

对于能够通过 Python 校验的公式或示例，优先使用程序验证。

- BF 字符串匹配下标。
- 三对角矩阵压缩存储公式。
- 循环队列边界判断。

用户问答需要区分：

## 15. 知识库不足的处理

如果问题超出课程知识库范围：

1. 判断本地检索证据不足。
2. 明确告知当前课程资料没有充分覆盖。
3. 允许 Agent 使用外部知识查询工具。
4. 清楚标注外部来源。
5. 不得将外部知识伪装成老师原文。

如果外部接口失败：

应该返回明确提示，而不是编造检索结果。

# 第七部分：真实代码执行与在线评测

## 20. 代码执行是核心要求

绝对禁止使用：

exec(user_code)
eval(user_code)

在 Django 应用进程中执行学生提交的任意代码。

不得通过普通 subprocess 在没有隔离机制的情况下运行不可信代码。

必须使用真正具备隔离能力的执行服务。


## 21. 代码执行服务适配

定义：

CodeExecutionProvider

统一接口：

execute(code, stdin, limits) -> ExecutionResult

提供两个适配器：

PistonExecutionProvider

Judge0ExecutionProvider

优先按照老师文件尝试 Piston。

但必须考虑 Piston 公共 API 的授权政策。

如果没有合法可用的公共接口：

不得伪造运行结果。

允许使用有授权的兼容执行服务。

Judge0 托管 API 可以作为替代候选。

是否可用必须经过实际验证。

若需要自托管额外运行时，应独立说明部署依赖，并先核对是否符合本课程对技术栈的限制。

Django 主系统不得因此切换技术栈。


## 22. 代码评测

至少实现：

- Python 代码输入
- 标准输入
- 标准输出
- 多测试用例
- 预期输出
- 实际输出
- 通过数量
- 错误数量
- 异常类型
- 执行时间
- 超时提示

执行限制至少包括：

- 时间上限
- 内存上限
- 输出大小上限
- 代码长度限制
- 测试用例数量限制
- 调用频率限制

不得允许用户代码访问 Django 项目的本地文件、数据库和环境变量。

需要明确告知学生代码会被发送到第三方执行服务。


## 23. 判题规则

由真实测试结果决定是否通过。

必须区分：

Accepted
Wrong Answer
Runtime Error
Syntax Error
Time Limit Exceeded
Memory Limit Exceeded
Judge Error

标准答案与隐藏测试用例必须由服务端管理。

不得将隐藏测试用例或预期答案完整发送到前端。

在自定义测试模式中，允许用户查看自己提交的输入输出。

标准判题模式必须按照题目规定进行。

不得只依靠大模型判断代码对错。

### 正确率定义

区分：

提交正确率
题目通过率

提交正确率：
正确提交数 / 全部有效提交数。

题目通过率：
至少完成一次正确提交的不同题目数 / 已尝试的不同题目数。

不能混淆两个指标。

报告中必须写清统计口径。


## 24. AI 错误诊断

学生代码执行失败后：

1. 保存真实执行结果。
2. 识别错误类型。
3. 定位可识别的错误位置。
4. 结合题目与测试结果分析。
5. 给出修复建议。
6. 引导学生再次尝试。

AI 可以解释错误，但不能修改判题结果。

AI 不能声称没有执行的代码已经通过测试。

修复建议优先采用分层提示：

Level 1：指出问题方向。

Level 2：指出可能出错的逻辑。

Level 3：解释修复方法。

Level 4：提供参考代码。


# 第八部分：自适应算法教学

## 25. 教学策略

- 不变量
- 状态
- 转移关系
- 数据结构特性
- 贡献计算
- 等价转化

# 第十部分：动态知识网络图

## 30. 核心创新目标

这是本项目最重要的原创增强功能之一。

将老师提供的课程知识库转化为一张动态、可交互、可追踪、能够反映学生知识掌握情况的网络图。

知识网络不是普通思维导图。

它必须同时表达：

1. 章节结构。
2. 知识点层级。
3. 概念之间的联系。
4. 先修依赖。
5. 当前掌握程度。
6. 学习进度。
7. 推荐学习路径。

系统应能够根据真实学习记录更新每个节点的视觉状态。


## 31. 图谱结构

至少建立：

Course
Chapter
KnowledgePoint
KnowledgeRelation

关系类型至少包括：

contains
prerequisite
related

其中：

contains：
章节包含知识点。

prerequisite：
学习当前知识前建议掌握的知识。

related：
概念之间存在关联，但没有严格先后关系。

先修图必须检查有向环。

如果存在循环依赖，应该进入人工复核。

不能把所有 related 关系都错误地当成先修依赖。


## 32. 节点稳定性

每个节点必须具有稳定 ID。

例如：

chapter_01
chapter_02
chapter_03
chapter_04

知识点使用稳定、可读的标识。

不能每次生成知识图谱都随机分配新 ID。

否则学生历史掌握数据无法正确关联。

图谱版本更新时，必须保留知识点 ID 映射与数据迁移规则。


## 33. 图谱覆盖范围

完整解析老师提供的四章知识库。

至少覆盖：

第一章：
数据基本概念、数据结构、逻辑结构、存储结构、ADT、算法基本特性、时间复杂度、空间复杂度。

第二章：
顺序表、随机存取、查找、插入、删除、单链表、头插法、尾插法、循环链表、双向链表。

第三章：
顺序栈、链栈、LIFO、循环队列、链队列、FIFO、队列判空、队列判满、队列操作。

第四章：
字符串、BF 算法、KMP、next 数组、数组行优先存储、列优先存储、对称矩阵压缩、三角矩阵压缩、三对角矩阵、广义表。

更细粒度的知识点应根据原始 PDF 内容继续完善。

不得遗漏原始文档中的主要知识概念。

UNDERSTANDING

黄色。

显示掌握指数和文字状态，不能仅依靠颜色传达信息。


## 35. 掌握度算法

掌握度必须来自真实学习数据。

建议第一版采用可解释的规则模型。

输入可以包括：

- 不同题目完成情况
- 最近答题表现
- 题目难度
- 独立完成程度
- 提示使用情况
- 复习表现
- 训练覆盖度

必须明确算法公式、参数和统计口径。

所有参数写入集中配置。

单次正确不得直接进入 MASTERED。

学习记录不足时，显示：

证据不足。

不要把没有充分证据的结果包装成精确掌握概率。

支持掌握度回退。

例如：

学生近期多次错误，掌握指数下降。

但下降必须有合理规则，不能简单随机变化。


## 36. BKT 知识追踪

在规则模型基础上增加 BKT。

需要支持：

- 初始掌握概率
- 学习转移概率
- 猜对概率
- 已掌握但答错概率
- 连续作答状态更新

如果没有足够的训练数据：

使用有明确来源与说明的先验配置。

不能假装模型已经经过大规模训练。

必须区分：

规则掌握指数
BKT 估计掌握概率

这两个数字不能混用。

BKT 作为可选估计器，通过 MasteryEstimator 接口接入。

避免将知识追踪算法与图谱渲染耦合。


## 37. 图谱动态点亮

学生第一次进入：

没有学习证据的节点呈灰色。

学生完成练习后：

代码评测成功
→ 保存 Submission
→ 更新对应知识点学习记录
→ 重新计算掌握指数
→ 保存掌握状态
→ 更新图谱节点颜色。

必须保证数据一致性。

建议使用 Django transaction.atomic 处理评测结果写入和相应业务状态更新。

涉及事务提交后才执行的操作使用 transaction.on_commit。

不得在数据库事务完成之前向前端宣称掌握度已经更新成功。


## 38. 父节点掌握度

章节节点的掌握度必须由下属知识点聚合。

建议采用有明确权重的加权计算。

但要避免：

仅掌握一个简单知识点，就让整个章节显示已掌握。

同时展示：

章节知识覆盖率
已学习知识点数量
熟练掌握知识点数量
章节综合掌握指数。

知识点没有足够证据时，不得自动计为完全掌握。

根节点根据所有章节汇总。

本地知识库检索仍然可以工作。

知识网络仍可查看。

学习记录仍可查询。

算法可视化仍可运行。

掌握度统计仍可计算。

代码执行取决于独立执行服务是否可用。

CrewAI 报告明确提示暂时不可生成。

不得把本地检索结果伪装成完整大模型问答。

不得返回虚构 Agent 执行结果。
